Core idea

What is Retrieval-Augmented Generation?

Retrieve relevant evidence, then generate from that evidence.

RAG retrieves useful information first and then gives that information to a generative model as context for the answer.

System flow

The RAG pipeline at a glance

Documents → chunks → embeddings → index → query → retrieval → prompt → answer.

A typical pipeline has two phases: prepare the knowledge base, then process user queries. The query side retrieves relevant chunks and builds a grounded prompt for generation.

Motivation

Why not rely only on model memory?

External knowledge can be newer, narrower, and easier to update.

A pretrained model may not know private, recent, local, or organization-specific information. RAG adds a controlled path to external sources that can be updated independently of model training.

Use cases

When RAG is useful

Use RAG when the answer should be grounded in retrievable evidence.

RAG is useful when answers should depend on a document collection, policy library, product manual, research corpus, knowledge base, or other source that changes over time.

Focus on the decision this step supports, not only the terminology.
Design choice

When RAG may be unnecessary

RAG is a design choice, not a requirement for every LLM task.

If the task is simple classification, rewriting, extraction, brainstorming, or general knowledge that does not require a specific knowledge source, retrieval may add complexity without much benefit.

Focus on the decision this step supports, not only the terminology.
Architecture

The four major parts of a RAG system

Ingest → index → retrieve → generate.

A practical RAG system can be understood as four parts: ingestion, indexing, retrieval, and generation. Evaluation and monitoring surround the entire pipeline.

1 · Ingestion

Load and clean knowledge sources.

2 · Indexing

Create vectors and store metadata.

3 · Retrieval

Find the best evidence for the query.

4 · Generation

Answer using retrieved context.

Ingestion

Knowledge sources

RAG begins with a well-defined knowledge collection.

The source collection may include PDF files, web pages, notes, FAQs, database exports, support documents, or structured records. The first goal is to make the content consistently readable.

Ingestion

Document ingestion

Preserve enough metadata to trace each chunk back to its source.

Ingestion converts source material into text plus useful metadata. The pipeline may also record source name, section, date, author, category, permissions, or document identifiers.

Preparation

Cleaning before indexing

Bad input creates bad retrieval even when the embedding model is strong.

Remove repeated headers, broken encoding, navigation text, empty sections, duplicated pages, and other noise that can reduce retrieval quality.

Chunking

Why chunk documents?

A chunk should be large enough to carry meaning and small enough to retrieve precisely.

Embedding an entire long document as one vector can blur many topics together. Chunking creates smaller retrieval units so the system can return focused evidence.

Chunking method

Fixed-size chunking

Start simple before moving to more complex chunking logic.

The simplest strategy divides text by a fixed number of characters, words, sentences, or tokens. It is easy to implement and useful as a baseline.

Chunking tradeoff

Chunk overlap

Overlap protects context, but excessive overlap increases cost and duplicates.

Overlap repeats a small portion of text between neighboring chunks so important ideas are less likely to be split across boundaries. Too much overlap creates redundancy and a larger index.

Chunk 1
A B C D EChunk 2
D E F G HChunk 3
G H I J K

Repeated boundary tokens preserve context across neighboring chunks.

Chunking method

Structure-aware chunking

Document structure often provides better boundaries than arbitrary character counts.

Instead of cutting only by size, a structure-aware strategy can split by headings, paragraphs, sections, code blocks, or document hierarchy.

Chunking method

Semantic chunking

Use semantic boundaries when topic shifts matter more than uniform chunk size.

Semantic chunking tries to keep related sentences together by detecting changes in meaning. It can improve coherence but costs more computation than fixed-size splitting.

Metadata

Metadata is part of retrieval

Text tells us what the chunk says; metadata tells us where it belongs.

Metadata can support filtering, source display, access rules, recency control, and debugging. A useful chunk is not only text; it also carries context about where it came from.

Representation

Embeddings in RAG

Embeddings make semantic retrieval possible.

An embedding model maps each chunk to a dense numeric vector. Similar meanings should be located near one another in the embedding space.

Focus on the decision this step supports, not only the terminology.
Model selection

Choosing an embedding model

The best embedding model is the one that retrieves your relevant evidence reliably.

Choose an embedding model based on language, domain, retrieval quality, vector dimension, speed, deployment constraints, and license. Test on your own retrieval examples instead of relying only on benchmark names.

Focus on the decision this step supports, not only the terminology.
Query processing

The query becomes a vector too

Document vectors and query vectors must live in the same representation space.

At search time, the user query is embedded with the same compatible embedding model used for the document chunks. The system then compares the query vector with stored chunk vectors.

Focus on the decision this step supports, not only the terminology.
Similarity

Cosine similarity

Higher cosine similarity usually means greater semantic similarity.

Cosine similarity compares vector direction rather than raw magnitude. It is common for text embeddings because semantically similar vectors often point in similar directions.

QueryABC

Vectors pointing in similar directions have higher cosine similarity.

Similarity

Dot product and Euclidean distance

Do not choose a similarity metric independently of the embedding model.

Some embedding models or indexes use dot product or Euclidean distance. The correct measure depends on how the model was trained and whether vectors are normalized.

Indexing

What is a vector index?

The index is the search structure built over the vectors.

A vector index organizes embeddings so nearest-neighbor search can be much faster than comparing a query against every stored vector.

Storage

What is a vector database?

A vector database adds data-management features around vector search.

A vector database stores embeddings and usually supports similarity search, metadata, filtering, updates, persistence, and retrieval APIs.

Comparison

Vector database vs relational database

Exact structure and semantic similarity solve different search problems.

Relational databases are designed around exact values, joins, constraints, and structured queries. Vector systems focus on nearest-neighbor similarity over high-dimensional vectors. Many applications use both.

Relational database

  • Exact values
  • Structured schema
  • Joins and constraints
  • SQL filters

Vector database

  • Semantic similarity
  • High-dimensional vectors
  • Nearest-neighbor search
  • Metadata filters
Retrieval method

Dense retrieval

Dense search is strong when meaning matters more than keyword overlap.

Dense retrieval uses embedding vectors to find semantically related text even when the query and document do not share the same exact words.

Retrieval method

Sparse retrieval and BM25

Keyword retrieval still matters in modern RAG systems.

Sparse retrieval emphasizes exact terms and term frequency. BM25 remains useful for identifiers, product names, rare terminology, codes, and precise lexical matches.

Retrieval method

Hybrid retrieval

Hybrid search is often useful when exact terms and semantic meaning both matter.

Hybrid retrieval combines dense semantic search with sparse keyword search. The results can be merged or reranked to benefit from both types of evidence.

Retrieval control

Metadata filtering

Filtering narrows the search space using known structured constraints.

Filters can restrict retrieval before or after similarity search. Examples include document type, date, product category, language, department, or access level.

Focus on the decision this step supports, not only the terminology.
Retrieval parameter

Top-k retrieval

More retrieved chunks are not automatically better.

Top-k controls how many retrieved chunks are passed forward. A larger k may improve recall but can add irrelevant context, increase prompt length, and raise cost.

Focus on the decision this step supports, not only the terminology.
Retrieval parameter

Similarity thresholds

Sometimes the correct retrieval result is no result.

A similarity threshold can prevent weak results from being treated as evidence. If nothing passes the threshold, the system can say that the knowledge base does not contain enough support.

Focus on the decision this step supports, not only the terminology.
Retrieval improvement

Reranking

Retrieve broadly, then rank more precisely.

A reranker scores a smaller set of retrieved candidates more carefully. The first retriever is fast; the reranker spends more computation deciding which evidence is most relevant.

Query transformation

Query rewriting

Better search queries can improve retrieval without changing the document index.

A query can be rewritten to remove ambiguity, expand abbreviations, add domain terminology, or produce a search-friendly version before retrieval.

Focus on the decision this step supports, not only the terminology.
Query transformation

Multi-query retrieval

Multiple search perspectives can recover evidence that one phrasing misses.

One user question can be converted into several related search queries. Results from those queries are combined to improve coverage.

Focus on the decision this step supports, not only the terminology.
Advanced retrieval

HyDE: retrieve from a hypothetical answer

HyDE changes the retrieval representation rather than the stored knowledge.

HyDE creates a hypothetical answer or document from the query, embeds that generated text, and uses it to search the real document collection.

Focus on the decision this step supports, not only the terminology.
Advanced retrieval

Parent-child retrieval

Retrieve small; provide enough surrounding context to answer well.

A system can retrieve small child chunks for precision but return their larger parent section for context. This separates the best unit for search from the best unit for generation.

Focus on the decision this step supports, not only the terminology.
Advanced retrieval

Contextual compression

Retrieval finds candidate evidence; compression can trim it.

After retrieval, a compression step can keep only the passages or sentences most relevant to the query. This can reduce prompt length and irrelevant context.

Prompt construction

Build the generation prompt

A good RAG prompt clearly separates instructions, context, and the user question.

The prompt usually contains the user question, retrieved evidence, source labels, and explicit instructions about how to use the evidence.

Generation

Grounding the answer

The retrieved context should constrain the generated answer.

Grounding means the answer should be supported by the retrieved context rather than invented from unsupported assumptions. The prompt can ask the model to say when evidence is insufficient.

Trust

Source attribution and citations

Retrieval is more useful when users can inspect the supporting evidence.

A RAG interface can show the source chunks, document names, links, or section labels that supported the answer. This makes verification easier.

Python workflow

A small built-in corpus

A tiny corpus makes every step visible.

We can understand RAG without a large external dataset. A small Python list of short documents is enough to demonstrate chunking, embeddings, similarity, and retrieval.

Python workflow

Install and import the basic tools

Keep the first implementation small and transparent.

A beginner-friendly local example can use sentence-transformers for embeddings, NumPy for similarity, and optionally FAISS for faster vector search.

Python · VS Code
pip install sentence-transformers numpy faiss-cpu
Python workflow

Create chunks with metadata

Keep the text and its source information together.

Represent each chunk as a dictionary with text and metadata. This simple structure makes it easy to inspect exactly what will be embedded and returned.

Python · VS Code
chunks = [
    {"text": "RAG combines retrieval with generation.", "source": "notes_1"},
    {"text": "Vector databases support similarity search.", "source": "notes_2"},
    {"text": "Reranking can improve the order of retrieved results.", "source": "notes_3"},
]

texts = [item["text"] for item in chunks]
print(texts)
Python workflow

Embed the chunks

After embedding, the corpus becomes searchable in vector space.

The embedding model converts the chunk texts into a matrix where each row is one vector. Normalizing the vectors makes cosine-style comparison straightforward.

Python · VS Code
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = model.encode(
    texts,
    normalize_embeddings=True
)

print(embeddings.shape)
Python workflow

Retrieve with NumPy

Brute-force search is fine for learning and very small collections.

For a small teaching example, NumPy can compute similarities directly. This makes the retrieval math easy to inspect before introducing a specialized index.

Python · VS Code
import numpy as np

query = "How does RAG search for useful information?"
query_vec = model.encode([query], normalize_embeddings=True)[0]

scores = embeddings @ query_vec
order = np.argsort(scores)[::-1]

for i in order[:2]:
    print(round(float(scores[i]), 3), chunks[i]["text"])
Python workflow

Inspect the top results

Debug retrieval before debugging generation.

Always look at the actual chunks returned for several queries. Retrieval quality is easier to improve when we inspect the evidence instead of looking only at a final generated answer.

Vector search

Move to FAISS when the corpus grows

An index changes search efficiency, not the basic RAG logic.

FAISS provides efficient nearest-neighbor search over vectors. The workflow stays conceptually the same: create vectors, add them to an index, embed a query, and search.

Python · VS Code
import faiss
import numpy as np

index = faiss.IndexFlatIP(embeddings.shape[1])
index.add(np.asarray(embeddings, dtype="float32"))

q = np.asarray([query_vec], dtype="float32")
scores, ids = index.search(q, k=2)

print(ids)
print(scores)
Python workflow

Metadata filtering in practice

Structured filters and vector similarity can work together.

A simple system can filter candidate chunks by metadata before similarity scoring. Production vector databases provide this capability through query filters.

Python · VS Code
allowed_source = "notes_2"

candidates = [
    item for item in chunks
    if item["source"] == allowed_source
]

print(candidates)
Python workflow

Build a simple RAG prompt

Prompt construction connects retrieval to generation.

Take the retrieved chunks, label each source, join them into a context block, and place that context beside the user question.

Python · VS Code
retrieved = [chunks[i] for i in order[:2]]
context = "\n\n".join(
    f"[{item['source']}] {item['text']}"
    for item in retrieved
)

prompt = f"""Use the context below to answer the question.
If the context is not enough, say so.

Context:
{context}

Question:
{query}
"""

print(prompt)
Generation workflow

Connect the prompt to a language model

Separate retrieval logic from model-provider logic.

The same retrieved context can be passed to a local model, hosted model, or API. Keep the retrieval layer modular so the generator can change without rebuilding the entire knowledge pipeline.

Python · VS Code
def generate_answer(prompt, llm_call):
    return llm_call(prompt)

Evaluation

Evaluate retrieval separately

If retrieval fails, generation cannot recover missing evidence reliably.

Retrieval can be evaluated before generation. Useful questions include whether a relevant chunk appears in the top-k results and how highly it is ranked.

Focus on the decision this step supports, not only the terminology.
Evaluation metrics

Recall@k, Precision@k, and MRR

Retrieval metrics help isolate search quality from answer quality.

Recall@k measures whether relevant evidence is found, Precision@k measures how much of the retrieved set is useful, and Mean Reciprocal Rank rewards placing the first relevant result near the top.

Focus on the decision this step supports, not only the terminology.
Evaluation

Evaluate the generated answer

A fluent answer is not automatically a grounded answer.

Generation can be checked for correctness, relevance, completeness, groundedness, and citation support. Human review is often valuable for important domain-specific questions.

Focus on the decision this step supports, not only the terminology.
Debugging

Common RAG failure modes

Treat RAG as a pipeline and locate the stage where quality breaks.

Failures can come from poor source data, weak chunking, bad embeddings, incorrect filters, low-quality retrieval, excessive context, weak prompts, or unsupported generation.

Focus on the decision this step supports, not only the terminology.
Debugging

Retrieval failure vs generation failure

Do not change the LLM when the real problem is retrieval.

If the correct evidence was not retrieved, improve search. If the correct evidence was retrieved but ignored or misused, improve prompt construction or generation.

Operations

Freshness and updates

RAG quality depends on keeping the index synchronized with the source of truth.

Knowledge changes. A production system needs a process for adding new documents, updating changed content, deleting stale chunks, and rebuilding affected embeddings.

Focus on the decision this step supports, not only the terminology.
Safety

Security: retrieved text can contain instructions

Treat retrieved text as evidence, not as authority over the application.

Retrieved documents are data, but they can contain text that looks like instructions. A RAG system should separate trusted system instructions from untrusted retrieved content.

Focus on the decision this step supports, not only the terminology.
Safety

Privacy and access control

Authorization belongs in retrieval and data access, not only in the final UI.

The retriever should not return information a user is not authorized to see. Access rules are most reliable when enforced before generation, not after sensitive text has already entered the prompt.

Focus on the decision this step supports, not only the terminology.
Operations

Latency and cost

A useful RAG system balances quality, speed, and cost.

Embedding the query, searching the index, reranking, adding context, and generating the answer all contribute to latency and cost. Measure each stage separately.

Focus on the decision this step supports, not only the terminology.
Recap

A practical architecture checklist

RAG works best when each stage is simple enough to inspect and test.

Define the knowledge source, clean it, choose chunking, add metadata, select embeddings, build the index, retrieve, rerank when useful, construct grounded prompts, evaluate, and monitor updates.
